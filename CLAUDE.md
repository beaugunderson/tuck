# Tuck — CLAUDE.md

A tiny, performance-obsessed macOS menu bar manager (Bartender replacement). Plain `swiftc`, no Xcode project. Built on macOS 26, notched 16" MBP.

## What it does
- Left-click the chevron → a floating horizontal strip (IceBar) of the hidden icons' **real glyphs**; click one to open it.
- Right-click the chevron → options: a checklist of manageable menu bar icons (checkmark = shown always; toggle a row to hide/show it by ⌘-dragging it across the separator via `ItemManager`, one at a time, so macOS never overflow-drops), then Show All, Launch at Login, How to Hide an Icon…, Quit.
- Toggling a row records a shown/hidden decision in the **active screen preset** (`ScreenPreset`, persisted in UserDefaults under `screenPresets` as `[key: {shown, hidden}]`, items keyed by `info` = `namespace:title`; items with no entry are left alone). `reconcile()` drags any entry sitting on the wrong side of the separator back, one at a time, driven by a poll (`pollTimer`, 5s). Fixes SwiftBar plugins that go null-output and return — their window title is the stable plugin filename, so `info` re-matches on return. A tick is one cheap enumeration; it re-enumerates only after an actual move, since each move shifts the separator.
- **Presets are keyed by menu bar width**, not display identity: `screenKey()` = the width in points of the screen behind `separatorItem.button?.window` plus `n` for a notch (`1728n` = this MBP, `3008` = the home ultrawide). Same width ⇒ same preset; a scaling change is a new key on purpose. `didChangeScreenParametersNotification` (debounced 1.5s, docking fires it repeatedly mid-relayout) calls `activateScreen()`, which seeds a never-seen key from the outgoing preset and reconciles. The key is read only at launch and on that notification, never per tick, so a "separate Spaces" setup that moves status item windows to the active display's bar can't flip presets as the mouse crosses screens. The checklist header shows `localizedName, Npt` for the screen being edited.
- Hiding: a wide "separator" status item shoves everything to its left off-screen; the user ⌘-drags icons across it. "Show All" makes the divider visible for arranging.

## Design tenet: near-zero idle work
No always-on event tap, no mouse tracking. Everything is click-driven except one recurring timer: the reconcile poll (`pollTimer`, 5s), which exists only while the active preset has entries and whose tick is a sub-ms window enumeration — so idle still measures **0.0% CPU / ~14 MB** (top real-mem; `ps` RSS reads ~43 MB counting shared framework pages). Enumerating once per preset entry per tick instead of once per tick measured 0.3–0.4%, so keep it to one. (Ice idles at 1.5–2.6% / 44 MB because of its always-on mouse-tracking tap — deliberately not ported.) The poll is a poll because macOS gives no other option — see the gotcha below.

## Architecture (Sources/)
- `main.swift` — AppDelegate: status items, the chevron/options handlers, `captureGlyphs` (composite capture + per-item crop), the help dialog + diagram.
- `IceBar.swift` — the floating horizontal strip (borderless NSPanel + sampled-color background + hover cells, visual-effect fallback). Centered on the chevron, clamped to screen. 0.25s debounce so clicking the chevron while open closes it (not close-then-reopen). `onVisibilityChange` emits only real open/close transitions, so every dismiss path keeps the chevron in sync.
- `Chevron.swift` — fixed-size template glyph rotating left → down while IceBar is open. A 160ms smoothstep animation uses a transient 60Hz timer that invalidates on completion; no idle work. Reverses from the current angle if interrupted. Reduce Motion skips interpolation. Don’t animate the whole status-button layer (it can affect highlights/tint), or swap differently sized SF Symbols (it shifts neighboring items).
- `MenuBarAppearance.swift` — on-open sampling of the Window Server’s `Menubar` background window near the chevron, on the button’s display. Opaque sampled RGB keeps captured white glyphs readable in light system mode with dark/colored wallpaper; control appearance follows the sample’s brightness. If unavailable, fall back to the status button’s appearance and menu material. No timer or capture while closed.
- `Updater.swift` — opt-in updates (`checkForUpdatesAutomatically` in UserDefaults, off by default). The latest version is read from the redirect chain of `tuck.bar/download`, which passes through `…/releases/download/v<version>/Tuck.zip`; no GitHub API.
    - An install that has not been asked (`askedAboutUpdates` unset, switch off) gets one alert two seconds after launch offering to turn the switch on.
    - A download is staged only if it satisfies `Updater.requirement` (Tuck's identifier, this team's Developer ID, `notarized`) and its Info.plist version equals the one the URL named. Nothing installs until "Restart to Update" is chosen; then `replaceItemAt` swaps the bundle and the normal restart path relaunches.
    - Automatic checks are a one-shot timer (15s after launch, then daily) that exists only while the switch is on, so the idle tenet holds. Local builds are version 0.1.0 unless `TUCK_VERSION` is set, so a check from one offers the current release over `build/Tuck.app`.
    - `Tests/UpdaterTests.swift` covers version parsing and comparison. The unpack, verify, and install steps need a real notarized archive; `Tests/Manual.md` has the scenarios. Little Snitch blocks an unknown test binary's outbound requests, so a throwaway harness cannot reach the network on this Mac.
- `AgentBar.swift` — macOS 27: AX enumeration of `MenuBarAgent`'s window (which apps have icons on the bar). `AllowList.swift` — macOS 27: reads and writes the per-app "Allow in the Menu Bar" switches. See "macOS 27" below.
- `ItemManager.swift` — ported from Ice's MenuBarItemManager: synthetic-CGEvent click + ⌘-drag move + temp-show/rehide. Event taps here are transient (per-op, 50ms) → no idle cost. `tlog()` writes `/tmp/tuck.log` for debugging.
- `Bridging.swift` / `Private.swift` — private SkyLight (CGS) window APIs + capture, bound via `@_silgen_name`.
- `WindowInfo` / `MenuBarItem` / `MenuBarItemInfo` — Ice's item model (trimmed).
- `EventTap` / `MouseCursor` / `TaskTimeout` / `Support.swift` (Logger/Constants shims) — ported Ice utilities.

## Load-bearing gotchas
- **Capture the array variant**: `CGWindowListCreateImageFromArray` renders far-off-screen items; the single-window `CGWindowListCreateImage` returns nil for them. Both are `unavailable` in the macOS 26 SDK — bind via `@_silgen_name` (Ice's protocol shim no longer compiles). Needs Screen Recording.
- **Track temp-shown items by `windowID`, not `info`**: Control Center gives ~a dozen items the identical title "Item-0" → same `MenuBarItemInfo`, so info-based lookup grabs the wrong item and the rehide strands the shown one on the bar forever.
- Owner attribution is useless (everything reports "Control Center"); map window→app by frame-matching the AX tree if you need real names. `AXNames.swift` does this for the right-click checklist: walk every app's `AXExtrasMenuBar`, match each item to a window by left edge. The window-server *connection* owner is also useless — `CGSGetWindowOwner`→`CGSConnectionGetPID` returns Control Center's pid (36740) for every item, so there is NO window-server route to the real app; AX frame-matching is the only bridge, don't re-try the CGS route. Do it in parallel (`DispatchQueue.concurrentPerform`) over all processes with a per-app `AXUIElementSetMessagingTimeout` (0.15s) — a serial main-thread walk beach-balls for seconds; parallel is ~200ms for two dozen items.
  - Prefer `MenuBarItem.displayName` for the row label and only fall back to the AX-resolved owner when `displayName` is a placeholder (`Item-N`, a UUID, empty). `displayName` already names Control Center's own modules (Wi-Fi, Battery, Focus…) better than AX, which just reports "Control Center" for them.
  - Some agents own a status item yet are background-only (`.prohibited`, e.g. ZeroTier) or have an empty `localizedName` (old Intel apps, e.g. ControlPlane — fall back to the bundle name). Don't filter by activation policy. An app that publishes nothing to AX at all (ZeroTier's element returns zero attributes) is unresolvable — no bridge exists; it shows as "Unknown".
- "Shown always" vs "hidden" is decided by position relative to the separator (`item.frame.midX > separator.frame.maxX`, plus `minY < 100` to exclude overflow-dropped items), never `isOnScreen` — an animating or dropped item lies about being on screen.
- macOS-*dropped* items (parked at y≈1116, no window) can't be captured/clicked by anyone — keep items windowed-on-the-row. macOS drops the overflow when the right strip fills; on this Mac the usable strips are `0–771` (left of notch) and `956–1728` (right), notch `771–956`. Keep hidden icons windowed off-screen-left (still capturable) rather than letting them overflow-drop.
- **No Accessibility event fires when a status item is *added*** — only `AXUIElementDestroyed` on removal. Verified across the owning app element, the Control Center host process, and the `AXExtrasMenuBar` container itself, over ten notification types (created / children-changed / layout-changed / …). So pin-restore *cannot* be event-driven off the reappearance; the 5s poll is the only way to notice an item is back. Don't waste a session trying to replace the poll with an AXObserver on "created" — it silently never fires.

## macOS 27: the window model does not apply
- **Status items have no windows on macOS 27.** `MenuBarAgent` (`/System/Library/CoreServices/MenuBarAgent.app`) draws every app's item inside one full-width layer-24 window; `CGSGetProcessMenuBarWindowList` returns only the Window Server's `Menubar` window and no layer-25 item windows exist, Tuck's own included. Window enumeration, per-window capture, and `button.window`-based geometry all return nothing.
- **A status item too wide to fit is removed from the bar; it does not push its neighbors off-screen.** Measured on the 3008pt display with app menus ending at x=562: a 1400pt item shoved the 14 items on its left to x=700, a 1600pt item vanished and the others snapped back. Removed items report an AX frame just below the screen (y≈1680–1695).
- Accessibility is the enumeration route: the `MenuBarAgent` app's `AXWindows[0]` children are one container per item (frame on the bar row), and each owning app's `AXExtrasMenuBar` still lists its items with matching frames, which gives real owner names.
- **How Tuck runs on 27** (`AgentBar.isActive`: macOS 27 or later with `MenuBarAgent` running): hiding is per app through `AllowList`, which flips the app's "Allow in the Menu Bar" switch. There is no divider item, no strip, no capture, no synthetic input, and no poll; only the chevron exists.
    - A preset's `hidden` set holds one `MenuBarItemInfo` per hidden app (`<bundle id>:` with an empty title). `applyHidden()` switches off the active preset's hidden apps and switches on every other app that any preset hides (`managedBundles`); an app the user switched off in System Settings is in no preset and is never touched.
    - Left-click = `setPeeking`: switch every managed app on so the real icons rejoin the bar where they belong; a one-shot 10s timer hides them again unless the pointer is in the menu bar. Show All does the same without the timer.
    - `ItemOrder.group` runs before every switch flip: it rewrites the hidden apps' saved positions in `com.apple.MenuBar`'s `TrailingItemPreferredPositions` so they sit, in their existing order, left of every other item. The agent ignores a position write for an item that is on the bar (no live move, and none after the app relaunches) but uses it when the item rejoins the bar after being switched off, so the icons come back grouped. An app ticked back to always-shown stays in that left group until ⌘-dragged.
    - Position keys are `status:<owner>::<autosave name>`; the owner is the bundle identifier for most apps and the app's name for some (`status:Tuck::tuck.toggle`), so `itemOwners` passes both.
    - Quitting switches every managed app back on (`applicationWillTerminate`), because a hidden app has no icon to click while Tuck is gone. A crash or `kill -9` skips that; the next launch re-applies the preset.
    - The right-click checklist is one row per app: apps with an item in the agent's AX tree, then hidden ones. System modules (agent-owned items) are not listed; the allow list has no rows for them.
    - Tuck needs **Full Disk Access** for this: without it `defaults export` of the Control Center group domain fails from Tuck's process and the menu offers "Enable Full Disk Access for Tuck…". Accessibility is still needed for the checklist; Screen Recording is not used on 27.
    - `AllowList.apply` exports first and skips the import when nothing differs, so a no-op costs one `defaults` spawn. `Tests/AllowListTests.swift` covers the plist transform.
    - Presets saved on macOS 26 hold `shown` entries keyed `com.apple.controlcenter:<window title>`; the 27 path reads only `hidden` entries with an empty title, so those are inert.
    - Untested: notched display, multiple displays.
- **"Allow in the Menu Bar" hides and shows an app's icons live, with no "«" and no mouse, when the list is written with `defaults import`** (measured on 27.0.1 with a throwaway status item app; three hide/show cycles, each applied within ~1.2s):
    - Export the domain by path (`defaults export "<…>/group.com.apple.controlcenter" -`), flip `isAllowed` for the bundle inside `trackedApplications`, and `defaults import` the whole domain back. The agent picks it up without a restart. Granularity is per app: all of an app's items hide together.
    - **Killing the user's `cfprefsd` (`killall cfprefsd`) stops the agent hearing about imports** until `MenuBarAgent` itself restarts: the file changes, `defaults` exits 0, and the bar does not move. Measured both ways with SoftRAID's icon; waiting and launching another status item app do not heal it.
        - Something at login does exactly that on this Mac: launchd logged the user's `cfprefsd` "exited due to SIGKILL | sent by killall" 19 seconds after it started and 3 seconds after the agent did, so the agent was deaf from boot. The caller is unidentified; no login program or installed app contains the command as a plain string.
            - `Tools/killwatch.swift` traces it without root: it polls the process table and logs the parent chain and arguments of every `killall`. LaunchAgent `com.beaugunderson.tuck-killwatch` runs it for 240 seconds at each login, appending to `~/Library/Logs/tuck-killwatch.log`; the line to read is the `FOUND` block whose arguments name `cfprefsd`.
            - Once the caller is known, remove the trace: `launchctl bootout gui/$(id -u)/com.beaugunderson.tuck-killwatch`, then `trash` the plist in `~/Library/LaunchAgents` and `~/.local/libexec/killwatch`.
        - Tuck heals it: `AgentBar.isDeaf` is true when `MenuBarAgent` started before the user's `cfprefsd` (both start times from the kernel process table, `Processes`), and `restartAgentIfDeaf` then sends the agent a SIGTERM; launchd relaunches it and it reloads the list from the file. It runs after every allow-list apply and once 30 seconds after launch.
        - The check runs after the write because `defaults` starts a daemon when none is running; a missing daemon is never treated as deaf, since an agent restarted then would again be older than the daemon it wakes.
        - Judging deafness by whether the bar changed (an AX comparison two seconds after a write) fails both ways: a second click inside the two seconds cancels it, and at login the agent is slow enough to look deaf when it is fine.
    - `cfprefsd` logs `rejecting read`/`rejecting write` for this domain on every `defaults` call, working or not (the kernel refuses its preflight with "would require prompt" and `defaults` reads and writes the file directly). Those lines are not a symptom.
    - This is what Bartender 7 does (strings in its beta: `GoldenGateMenuBarAgentVisibilityManager`, `trackedApplications`, `/usr/bin/defaults`, "cfprefsd import failed", "Full Disk Access is required to control the menu bar"). It moves items the same way, by writing `TrailingItemPreferredPositions` in `~/Library/Group Containers/com.apple.MenuBar/Library/Preferences/com.apple.MenuBar.plist`, whose keys are `status:<bundle id>::<autosave name>` (SwiftBar's are the plugin paths) and `module:<name>`. Position writes are untested here.
- **The drag-off route into the same state is a trap** (same test app):
    - ⌘-dragging an icon off the bar disallows its app live (`MenuBarAgent` logs "Disallowed application"); the item stays alive, off the bar, and `AXPress` on it still opens an `NSMenu`, at the screen's top-left corner.
    - After a drag-off, nothing re-allowed it live: not the System Settings switch, not relaunching the app (the agent logs "Creating status item …, isAllowed: false" from its in-memory registry and re-persists that), not rewriting `trackedApplications`.
    - What does restore one: set `isAllowed` true in the stored list, then restart `MenuBarAgent` (launchd relaunches it and it reloads the list; every icon redraws). Brought back ABDownloadManager and SoftRAID.
    - The state is `trackedApplications` (a binary plist of alternating key/value) in `~/Library/Group Containers/group.com.apple.controlcenter/Library/Preferences/group.com.apple.controlcenter.plist`. `UserDefaults(suiteName:)` on that group returns nothing for a non-member, and a path-based `defaults write` lands in the file without notifying the agent.
    - `com.apple.MenuBarAgent.VisibilityRestrictionServer` rejects connections without an Apple-private entitlement ("Connection missing entitlement").
- AppKit's 27.0 SDK adds no hide/overflow API on `NSStatusItem` (only `expandedInterfaceDelegate`/`expandedInterfaceSession`). `MenuBarAgent` has its own overflow ("Show Hidden Menu Bar Items", `MenuBarOverflowComponent`, `alwaysHidden`/`alwaysVisible` modes) and a `com.apple.MenuBarAgent.VisibilityRestrictionServer` XPC service; neither has been driven from Tuck.
- **Spacer items trigger the native overflow, which Tuck does not use** because the system "«" button then sits at the far left of the bar (measured, 3008pt display, iTerm frontmost, menus ending x=562): three blank status items of 615pt each, placed where the separator sits, collapsed all 14 icons on their left behind the system "«" button at x=586. Clicking that button draws the hidden icons live over the app menus (x=209–579) and relabels it "Hide Menu Bar Items"; a second click collapses them. The icons are real and clickable, so no capture or temp-show is involved.
    - One item cannot do it: a single item of 1500pt or more is removed from the bar (1400pt fits). Split the width across several items.
    - Sizing is exact. 3×600 left two icons visible; 3×630 moved one spacer to the left of the overflow group and 3×700 dropped 7 icons from the AX tree entirely. The target total is the gap between the separator position and the end of the app menus, minus the 17.5pt button.
    - Create the spacers narrow and then set `length`; three items created at 615pt never appeared on the bar row.
    - The "«" button exposes no AX actions (`AXPress` returns -25206); only a mouse click toggles it. Its AX description is "Show Hidden Menu Bar Items" / "Hide Menu Bar Items".

## Build / sign / permissions
- `./build.sh` → cross-compiles `Sources/*.swift` for **arm64 and x86_64**, explicitly targeting **macOS 15.0** for both, combines with `lipo`, assembles `build/Tuck.app`, signs with Developer ID (`Developer ID Application: Beau Gunderson (D7UFB67V5Z)`). Developer ID keeps TCC grants across rebuilds; ad-hoc loses them every rebuild. `Tests/check-bundle.sh` verifies both slices, minimum OS metadata, and signatures before release notarization.
- Needs **Accessibility** (enumerate/move) + **Screen Recording** (capture glyphs). Newly granted Screen Recording may need a quit/reopen. Missing permission or total glyph-capture failure now presents Settings/Restart guidance; partial failures use a question mark, never the misleading Control Center owner icon. Right-click also offers Icon Capture Help and Restart. Restart uses LaunchServices with `createsNewApplicationInstance` and only terminates the old process after launch succeeds. Stale grants after an identity change: `tccutil reset {Accessibility|ScreenCapture} com.beau.tuck`.
- `bash Tests/run.sh` compiles color/geometry regression checks for both architectures and executes each supported slice (x86_64 via Rosetta on Apple silicon if installed); explicitly reports runtime skips. `Tests/Manual.md` covers real TCC, relaunch, and display/appearance scenarios.

- **Release by pushing a tag, never by running `release.sh` locally**: `git tag vX.Y.Z && git push origin vX.Y.Z` triggers `.github/workflows/release.yml` (macos-15 runner), which tests, runs `release.sh`, and bumps the cask in `beaugunderson/homebrew-tap`. `release.sh` creates the tag itself through `gh release create`, so a local run publishes the release and then makes the workflow fail at "a release with the same tag name already exists" with the cask step skipped.

## Microsite / domain

- `site/` is the static microsite at `https://tuck.bar`, hosted on Netlify project `tuck-bar` (`8a0e0c9f-1fac-4490-acbe-b4b26922d834`). No build step or runtime dependencies; `netlify.toml` publishes `site/`. Keep the free-forever promise. Browser regression checks: `Tests/site-browser.js` via `playwright-cli run-code --filename` against a local/deployed page.
- Keep site copy compact and in Beau’s voice: use the actual Bartender motivation, no decorative slogans or forced headline breaks, say “Free forever” once, omit architecture names from compatibility text, and keep Ice credit without the tiny bottom footer. The header chevron reveals a native `<details>` easter egg on mouse hover, keyboard, or tap; retain no-JS and Reduce Motion support. Regenerate `site/social.png` with `Tests/site-social.js` against the local preview when hero copy/layout changes.
- `/download` redirects (302, no-store) to GitHub `/releases/latest/download/Tuck.zip`. `release.sh` uploads both `Tuck-VERSION.zip` (Homebrew) and identical `Tuck.zip` (website). Don’t hardcode a version in the site or add a rate-limited client-side GitHub API dependency.
- Release **0.1.3+ is universal (arm64 + x86_64), macOS 15+**. Site, Info.plist, both load-command minima, and Homebrew (`:sequoia`) agree. Earlier 0.1.2 was arm64-only despite older, incorrect minimum-OS metadata. Don’t drop the explicit build targets: SDK/host defaults silently raise the minimum OS.
- Domain registered by Beau at Spaceship. **Keep Spaceship’s DNS** (`launch1.spaceship.net`, `launch2.spaceship.net`): `@ A 75.2.60.5`, `www CNAME tuck-bar.netlify.app`, TTL 300. Netlify serves the site, not the DNS. Switching nameservers left Spaceship’s DNSSEC DS in place and caused SERVFAIL; reverting preserved DNSSEC. The temporary Netlify DNS zone was deleted. Don’t migrate nameservers for routine Netlify setup.
- Spaceship API credentials are in 1Password item **spaceship API key** (username = API key, password = API secret). Python urllib gets a Cloudflare 403/error 1010, but **fetch-hard’s first-rung `curl_cffi` transport (`impersonate='safari184'`, `verify=certifi.where()`) works with the same API credentials**. fetch-hard CLI itself lacks auth-header flags; use that transport directly for authenticated API calls, keep credentials in memory, disable redirects, and never send them through third-party reader/proxy fallbacks.
